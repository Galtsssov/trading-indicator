# Этап 2.1 — первая рабочая версия исследовательского конвейера (MVP)

> Исторический документ. Код этапа 2.1 (`study.py`, `report.py`, `configs/mvp.toml`) заменён платформой
> этапа 2.2 — см. [stage-2.2.md](stage-2.2.md). Чтобы воспроизвести отчёт nif_v1: `git checkout 9bf3969`.

Конвейер проверяет главную гипотезу этапа 1 (NIF) на реальных данных Binance и сам пишет отчёт.
Следует [архитектуре этапа 2](platform-architecture.md); ниже — что реализовано и почему так.

## Как запустить

```bash
pip install -e ".[dev]"
```

```bash
pytest -q
```

```bash
python -m qlab all
```

`all` = `fetch` (скачать архив, проверить sha256, собрать Parquet) → `quality` (отчёт о качестве) →
`study` (исследование, графики, отчёт, запись в журнал). Шаги можно запускать по отдельности.
Результат: `reports/nif_v1/REPORT.md`, графики в `reports/nif_v1/figures/`, сырые числа в
`results.json`, качество данных в `quality.json`, журнал всех прогонов — `reports/ledger.jsonl`.

На GitHub то же делает workflow **research**: вкладка Actions → research → Run workflow.
Отчёт коммитится в репозиторий автоматически.

## 1. Структура

```
configs/mvp.toml          все параметры исследования (пререгистрация)
src/qlab/
  config.py               загрузка TOML, хэш конфига
  data/binance.py         план файлов архива, загрузка с повторами и sha256, разбор CSV → Parquet
  data/quality.py         покрытие, пропуски, дубли, некорректные свечи, выбросы, вердикт годности
  dataset.py              1m → 5m/15m, OI и funding as-of по времени публикации, контекст BTC
  features/__init__.py    реестр признаков: контракт, автопоиск файлов, порядок по зависимостям
  features/atr.py …       по файлу на признак: atr, vwap, volume, oi, session, btc
  events/sweep.py         Liquidity Sweep High/Low (параметризуемый, только прошлые данные)
  outcomes.py             что произошло после события: R-уровни, MFE/MAE, время, издержки
  controls.py             контрольная выборка: тот же час и та же дециль волатильности
  stats.py                метрики, бутстреп по дням, выбор теста, размер эффекта, поправка BH
  study.py                исследование NIF: группы A/B, сетка устойчивости, вердикт по правилу
  report.py               markdown-отчёт и графики
  cli.py                  команды fetch / quality / study / all, журнал прогонов
tests/                    23 теста: причинность, парсеры, датасет, свипы, исходы, статистика, сквозной
.github/workflows/        тесты на push; исследование на реальных данных по кнопке
```

Новый признак = новый файл в `src/qlab/features/` с декоратором `@feature`. Ядро находит его само,
проверяет зависимости и включает в тест причинности.

## 2. Инженерные решения

| Решение | Почему |
|---|---|
| У каждого значения есть время доступности: бар — `available_at` (закрытие), OI — `oi_available_at` (снимок + задержка публикации), funding — `funding_available_at` | Заглядывание в будущее исключено устройством данных, а не аккуратностью автора |
| OI и funding присоединяются as-of по `available_at`; OI старше 30 мин — неизвестен | В строку попадает только то, что было опубликовано к закрытию бара |
| Тест причинности для всех признаков и событий: расчёт на полной и на обрезанной истории должен совпасть | Ловит look-ahead автоматически, включая будущие признаки |
| Свип по экстремуму **прошлых** баров (без фракталов с правыми барами) | Фрактал подтверждается задним числом — частый источник ложных бэктестов |
| Вход — открытие первой минуты после закрытия бара свипа; путь — минутные свечи; цель и стоп в одной минуте → стоп | Консервативно и без подглядывания внутри бара |
| События с разрывом минутных данных исключаются с указанием причины | Не «чиним» данные молча; всё исключённое видно в отчёте |
| Контрольная выборка по часу и децили ATR | Без неё «эффект свипа» может оказаться сезонностью волатильности |
| Выбор теста по данным: нормальность отвергнута → перестановочный тест; плюс Манн–Уитни, KS, χ²/Фишер | Исходы барьеров дискретны и заведомо не нормальны |
| Доверительные интервалы — блочный бутстреп по дням | События одного дня зависимы |
| Размер эффекта: ΔE в R с CI, Cliff's δ, Cohen's d; порог практической значимости 0.05R | Решение принимается не по p-value |
| Поправка Бенджамини–Хохберга по всему семейству прогонов (3 монеты × 2 ТФ × 4 глубины) | Множественные проверки |
| Правило вердикта и все параметры зафиксированы в конфиге до первого запуска | Защита от подгонки; новая идея — новый конфиг и новая запись в журнале |
| Диагностический прогон с нулевой задержкой OI отдельно помечен «не торгуемо» и не влияет на вердикт | Отделяет «механизма нет» от «механизм есть, но данные запаздывают» |
| Журнал прогонов (хэш конфига, версия данных, коммит) в git | Ни один прогон не теряется; основа для учёта числа попыток |
| Стек: pandas + numpy + scipy + matplotlib + Parquet; без БД и серверов | Хватает с запасом: полный прогон одной пары на 6 годах 1m — секунды |

## 3. Ограничения MVP

- OI только с Binance, снимками раз в 5 минут; задержка публикации задана (5 мин), а не измерена.
- ΔOI измеряется за 3 бара до момента решения, а не строго за бар свипа: на 5m часть изменения OI
  на самом свипе ещё не опубликована. Поэтому есть диагностический прогон без задержки.
- Ликвидаций нет: падение OI — только их прокси.
- Сессии — фиксированные часы UTC без перехода на летнее время.
- Издержки — фиксированные (тейкер 0.05% + проскальзывание 0.02% за сторону), не зависят от стакана.
- Одна сделка на событие (цель/стоп/время). Частичных выходов, безубытка, лимитных входов пока нет.
- Нет разбивки на обучающий/проверочный/отложенный периоды. Параметры не подбирались, но
  отложенный период для будущих гипотез нужно выделить до следующих исследований.
- Feature Engine считает признаки заново при каждом запуске (без кэша) — сейчас это быстро.

## 4. Риски, которые могут исказить результаты

| Риск | Чем грозит | Что сделано / что нужно |
|---|---|---|
| Реальная задержка публикации OI больше 5 мин | Скрытое заглядывание в будущее → завышенный эффект | Консервативный запас; нужно измерить по живому потоку |
| Неверное понимание метки времени снимка OI (начало или конец периода) | То же | Диагностика lag=0 показывает чувствительность; проверить по документации и живым данным |
| Пропуски и сбои архива (биржевые простои, неполные дни) | Ложные свипы на разрывах | Неполные бары не дают событий; разрывы в пути исключаются; отчёт о качестве |
| Формат архива Binance меняется (заголовки, мкс вместо мс) | Падение или тихая порча при разборе | Разбор с автоопределением заголовка и единиц эпохи; тест парсеров; sha256 |
| ETH, SOL, BTC коррелированы | Три «подтверждения» — по сути одно | Вердикт требует ETH и SOL; в отчёте отмечено |
| Перекрытие сделок внутри монеты | Завышенная значимость | Cooldown 12 баров, бутстреп по дням |
| Издержки занижены | Ложная торгуемость | Отдельная строка торгуемости; стресс издержек — на 2.2 |
| Смена режима рынка (2021 бык, 2022 медведь) | Эффект только в одном периоде | Разбивка по годам в отчёте |

## 5. Что показал первый прогон (30.10.2026)

Полный отчёт — [reports/nif_v1/REPORT.md](../reports/nif_v1/REPORT.md). Данные: свечи с 2020 года
(SOL — с сентября 2020), OI — с декабря 2021 (BTC — с сентября 2020), покрытие ≥ 99.8%.

1. **NIF не подтверждена.** ΔE = E[B] − E[A] от −0.03 до +0.04R во всех 6 парах, Cliff's δ
   пренебрежимый, ни одно сравнение не значимо после поправки. Так же при всех 4 глубинах свипа
   и при нулевой задержке OI (диагностика). То есть механизм не прячется за задержкой данных.
   Слабый намёк на SOL 5m (CI чуть выше нуля при двух глубинах, p после BH = 0.62) — ниже порога
   практической значимости. Подгонять под него параметры нельзя.
2. **Издержки съедают всё.** Контроль (случайный вход) после издержек: ≈ −0.68R на ETH 5m,
   −0.97R на BTC 5m, −0.22…−0.49R на 15m. При 1R = 1 ATR сделки на 5m с рыночным входом
   практически бессмысленны. Это подтверждает вывод 1 этапа 1.
3. **Побочное наблюдение (не пререгистрировано):** реверсия после свипа хуже случайного входа во
   всех 6 парах (ΔE от −0.04 до −0.13R, значимо). MAE у свипов систематически больше MFE, у контроля —
   нет. После свипа цена чаще продолжает движение, чем разворачивается (как у Osler, этап 1, вывод 4).
   Это **новая гипотеза** «продолжение после свипа». Проверять её только на отложенном периоде,
   объявив заранее.

## 6. Что обязательно сделать на этапе 2.2

1. **Разбивка истории** на обучающий / проверочный / отложенный периоды в конфиге, доступ к
   отложенному — только с записью в журнал. Без этого следующие гипотезы будут проверяться на уже
   просмотренных данных.
2. **Гипотезы в YAML** (Hypothesis Engine): условия поверх признаков, без правки кода. Перевести
   NIF, эталонную реверсию К36 и SMT в этот формат.
3. **Эталон К36** в каждом отчёте: свипы должны обыгрывать простую реверсию.
4. **Измерить реальную задержку OI**: записывать живой поток OI и ликвидаций Binance с отметкой
   времени получения. Заодно копится бесплатная история ликвидаций.
5. **Кэш признаков** по хэшу (версия признака + параметры + версия данных), когда признаков станет десятки.
6. **Стресс издержек и задержки входа** (×1.5 издержек, вход на 1 бар позже) — ворота 4 и 11 из архитектуры.
