# Этап 2. Архитектура исследовательской платформы

Документ продолжает [этап 1](../research/). Кода здесь нет — только устройство системы,
контракты модулей и порядок постройки.

## 0. Пять решений, на которых держится всё остальное

1. **Исследуем события, а не каждый бар.** Единица анализа — событие (свип, импульс, пробой)
   и исход сделки после него. Сначала быстрое «событийное исследование» (event study):
   исходы событий против контрольной выборки. Медленная симуляция сделок нужна только тем
   гипотезам, которые пережили событийное исследование. Так 95% идей отсеиваются за секунды,
   а не за часы.
2. **Каждое значение помнит, когда стало известно.** У каждой строки данных и признака есть
   `ts` (к какому моменту относится) и `available_at` (когда это реально можно было узнать).
   Всё соединяется только по `available_at`. Это главная защита от заглядывания в будущее:
   она работает за счёт устройства хранилища, а не за счёт аккуратности автора.
3. **Журнал всех экспериментов.** Каждый прогон каждой вариации записывается безвозвратно.
   Число попыток — входной параметр статистики (поправка на множественные тесты, Deflated Sharpe).
   Нельзя «забыть» неудачные варианты.
4. **Отложенный период под замком.** Последний участок истории физически недоступен
   исследовательским модулям. Открывается один раз на гипотезу, факт открытия пишется в журнал.
5. **Скучный стек, без серверов.** Python, файлы Parquet, DuckDB/Polars для запросов, YAML
   для гипотез, запуск из командной строки и по cron. Без баз данных, очередей, микросервисов
   и Airflow. Всё это можно добавить позже, когда возникнет реальная нужда. Архитектура держится
   на контрактах между модулями, а не на инфраструктуре.

```
Источники ─► Слой данных (Parquet, ts + available_at, версии)
                 │
                 ▼
        Feature Engine (граф признаков, кэш, тест причинности)
                 │
     ┌───────────┼────────────────┐
     ▼           ▼                ▼
 События     Режимы рынка     Разметка исходов (тройной барьер по 1m)
     └───────────┼────────────────┘
                 ▼
  Hypothesis Engine (YAML) ◄── Automatic Discovery (генерирует YAML)
                 │
                 ▼
  Event study ─► Backtest (модели исполнения) ─► Validation (ворота)
                 │                                   │
                 ▼                                   ▼
        Журнал экспериментов ◄──────────── Evaluation + Ranking ─► Отчёты
```

## Модуль 1. Источники данных

Уточнение к постановке: часть данных из списка «платные» у Binance **бесплатна**.
- **Taker buy/sell** есть прямо в свечах Binance (поле taker buy volume).
- **Дельту, CVD и footprint** можно точно собрать из бесплатных aggTrades (каждая сделка
  со стороной агрессора).
- **ATR, VWAP, сессии** — это не источники, а признаки, они считаются из свечей.

Платными по-настоящему остаются: история ликвидаций, полный стакан L2, тепловые карты стакана,
история опционов по страйкам.

Наличие, глубину и форматы архивов нужно проверить на первом шаге. Ниже — ожидания.

**Колонки таблицы:**
- **Важн.** — важность для главной гипотезы (NIF), от 1 до 5.
- **Без него?** — можно ли начать без этого источника.
- **История** — насколько сложно получить историю.
- **Прирост шанса на edge** — насколько источник увеличивает вероятность найти преимущество.

|---|---|---|---|---|---|

| Полный стакан L2 (Tardis.dev) | Абсорбция, спуфинг, устойчивость стакана | 2 | Да | Дорого, терабайты | Средний и дорогой |
| Тепловые карты стакана | Визуальная производная от L2 | 1 | Да | Производная от L2 | Низкий: та же информация, что в L2 |
| OI опционов по страйкам (Deribit через Tardis) | Притяжение к страйку перед экспирацией | 2 | Да | Платно | Средний, только ETH |
| Агрегированный OI и ликвидации по всем биржам | Полная картина плеча | 3 | Да: Binance — крупнейшая доля | Платно | Средний |

**Правило очерёдности:** платные данные покупаем только после того, как бесплатный прокси
(ΔOI вместо ликвидаций) покажет эффект. Если прокси не показал ничего, платный источник
вряд ли спасёт. С первого дня бесплатно записываем то, что потом не купить дёшево:
поток ликвидаций Binance и снимки стакана.

### Устройство слоя данных
- `raw/` — исходные файлы как скачаны, неизменяемые, с контрольными суммами.
- `clean/` — единая сетка 1m по UTC, Parquet с разбивкой по `источник/символ/месяц`,
  колонки `ts` и `available_at`.
- **Задержка публикации** задаётся в описании набора данных. Пример: OI за бар 12:05 считается
  известным не раньше 12:10 плюс консервативный запас.
- **Проверки качества**: дыры, дубли, нулевые объёмы, выбросы, переходы цены между биржами.
  Найденные проблемы пишутся в манифест, а не «чинятся» молча.
- **Версия набора данных** — хэш манифеста. Её записывает каждый результат.

## Модуль 2. Feature Engine

Признак — независимый модуль с объявленным контрактом. Ядро ничего не знает о конкретных
признаках. Оно читает их контракты, строит граф зависимостей, считает признаки в нужном
порядке и кэширует результат.

### Контракт признака

| Поле | Смысл |
|---|---|
| `name`, `version` | Уникальное имя. Версия повышается при изменении логики, после чего кэш и результаты помечаются устаревшими |
| `inputs` | Наборы данных и другие признаки, от которых зависит (из этого строится граф) |
| `params` | Параметры с допустимыми диапазонами: окно, порог, N баров |
| `timeframe` | На каком ТФ имеет смысл (1m/5m/15m/1h); ядро само агрегирует 1m |
| `warmup` | Сколько баров истории нужно до первого валидного значения |
| `outputs` | Колонки, типы и семантика: `float`, `bool`, `category`; единица — ATR, %, σ |
| `lag` | Через сколько баров после `ts` значение становится известным. Для swing по фракталу N — это N правых баров |
| `compute` | Чистая функция: таблица входов → колонки выходов. Без состояния, без сети, без чтения файлов |
| `description` | Одна строка: что меряет и зачем (ссылка на фактор этапа 1, например «A1») |

### Что ядро делает автоматически
- **Регистрация.** Чтобы появился новый признак, достаточно положить файл в `features/`.
  Ядро находит его само, правки в других местах не нужны.
- **Граф и кэш.** Ключ кэша — хэш версии признака, параметров и версии данных. Перерасчёт
  идёт только при изменении одного из них.
- **Тест причинности (обязательный, автоматический).** Ядро считает признак на полной истории
  и на истории, обрезанной в случайной точке t. Значения до момента t (с учётом заявленного
  `lag`) обязаны совпасть. Если не совпадают, признак подглядывает в будущее и регистрацию
  не проходит. Это ловит большинство ошибок look-ahead без ручного ревью.
- **Нормировка.** Стандартные производные (процентиль за 30 дней, z-score, значение в ATR)
  ядро строит для любого числового признака, без отдельного кода в каждом модуле.

### Начальный набор семейств (связь с факторами этапа 1)

| Модуль | Что даёт | Этап 1 |
|---|---|---|
| `atr`, `volatility` | ATR, процентиль режима, realized vol, сжатие | D1–D15 |
| `session` | Час недели, сессии, окна funding и экспираций, учёт DST | E1–E15 |
| `levels` | Swing N, PDH/PDL, Asia range, недельные уровни, круглые числа, equal highs | A1–A9 |
| `sweep` | Свип: глубина, время за уровнем, фитиль или тело, возраст уровня | A10–A13, A20 |
| `oi` | ΔOI за бар и окно, ΔOI на свипе, рост OI на подходе | B4, B5 |
| `funding` | Уровень, процентиль, время до расчёта | B1–B3 |
| `flow` | Дельта, CVD (фиксированный якорь), абсорбция | C1–C3 |
| `impulse` | Размер и скорость импульса, FVG | G1–G6 |
| `vwap` | Сессионный VWAP и VWAP от события, отклонение в σ | G12 |
| `trend` | Тренд 1h/4h, efficiency ratio | F1 |
| `cross` | Ход BTC в то же окно, SMT, корреляция, бета | J1, J15, C15 |
| `basis` | Перп против спота, Coinbase premium | B9–B11 |
| `range` | Позиция в дневном и недельном диапазоне, IB, Value Area | K1–K8 |

Ориентир — 300+ признаков с учётом параметров и нормировок.

## Модуль 3. Hypothesis Engine

Гипотеза — YAML-файл. Ядро превращает его в выборку событий, сделок и отчёт без
изменения кода. Пример (главная гипотеза NIF, сторона «реверсия»):

```yaml
id: nif_reversal_v1
origin: research/02-combinations.md#К1
symbols: [ETHUSDT, SOLUSDT]
timeframe: 5m
event: sweep.swing_high            # из какого признака-события стартуем
side: short                        # реверсия против свипа вверх; зеркальная гипотеза — отдельный файл
when:
  - sweep.swing_n >= 24
  - sweep.bars_beyond <= 2
  - sweep.closed_back == true
  - oi.change_pct_on_sweep < -0.5
  - atr.pctl_30d > 70
  - session.name in [us_open, london]
  - abs(vwap.dist_atr) < 0.5
entry: {type: market, at: next_open}
exit:
  stop: {type: atr, k: 1.0}
  take: [{r: 1.0, size: 0.5}, {r: 2.0, size: 0.5}]
  breakeven_after_r: 1.0
  time_stop_bars: 12
params:                            # диапазоны для теста чувствительности; каждая точка — запись в журнале
  sweep.swing_n: [12, 24, 48]
  oi.change_pct_on_sweep: [-0.25, -0.5, -1.0]
control: matched                   # контроль по часу недели и процентилю ATR
compare_to: [baseline_reversal_v1] # эталон К36: гипотеза обязана его обыграть
```

**Принципы:**
- **Безопасный язык условий.** Сравнения, `and`, `or`, `in`, `abs`, `between`, ссылки на
  признаки. Никакого исполнения произвольного кода из YAML.
- **Проверка до запуска.** Неизвестный признак, неправильный тип, ТФ без данных — ошибка
  сразу, до расчёта.
- **Хэш гипотезы** — от нормализованного текста. Одна и та же гипотеза с другим комментарием
  не считается новой.
- **Контроль и эталон обязательны.** Гипотеза без `control` не запускается.
- **Discovery пишет такие же YAML-файлы.** Ручные и автоматические гипотезы проходят один и тот же путь.

## Модуль 4. Backtest Engine

Два уровня, один набор данных.

**Уровень 1 — событийное исследование (быстрое).** Для каждого события считаются исходы
по тройному барьеру на нескольких сетках (k = 0.5, 1, 2 ATR; время 6, 12, 24 бара), MFE и MAE,
сырые доходности. То же — для контрольной выборки. Ответ на вопрос «есть ли вообще разница»
за секунды, без модели исполнения.

**Уровень 2 — симуляция сделок (честная).** Только для гипотез, прошедших уровень 1.

| Элемент | Как моделируется |
|---|---|
| Путь цены | Сделка идёт по 1m-барам внутри 5m/15m. Если стоп и тейк в одном 1m-баре — считаем, что **сначала сработал стоп** (консервативно). Опционально уточнение по aggTrades |
| Рыночный вход | Открытие следующего бара + проскальзывание: фиксированное, пропорциональное волатильности или по реальной глубине из aggTrades (три модели, по умолчанию — средняя) |
| Лимитный вход | Исполнен, только если цена **прошла сквозь** лимит хотя бы на 1 тик (касание не считается — очередь). Неисполненные заявки учитываются отдельно — так видно adverse selection |
| Комиссии | Maker и taker по профилю (VIP-уровень — параметр). Funding списывается при удержании через 00/08/16 |
| Стопы | ATR, структурный (за экстремумом свипа + буфер), фиксированный %, трейлинг |
| Тейки | В R, в ATR, по уровню (VWAP, противоположная граница), частичные закрытия |
| Управление | Перевод в безубыток после X R, time stop, выход по противоположному сигналу |
| Перекрытие | Одна позиция на символ. Совпадающие сигналы ETH и SOL помечаются как одна ставка |
| Задержка | Параметр «вход на k баров позже» — тест на хрупкость |

Модели исполнения — подключаемые модули с одним контрактом: «заявка + путь цены →
исполнения». Новая модель не требует правок ядра.

## Модуль 5. Validation Engine

Последовательные ворота: первая непройденная проверка останавливает конвейер, и вердикт
записывается с причиной. Порядок — от дешёвой проверки к дорогой.

### Разбивка истории (фиксирована в конфиге, одна на весь проект)

| Участок | Период (ориентир) | Кто имеет доступ |
|---|---|---|
| Discovery | 2021-01 — 2022-12 | Discovery и ручной поиск |
| Validation (OOS) | 2023-01 — 2025-06 | Только Validation Engine |
| Holdout | 2025-07 — сегодня | Один раз на гипотезу, с записью в журнал |

Если история OI в архиве короче, границы сдвигаются, но пропорции сохраняются.

### Ворота

| # | Проверка | Что делает | Критерий отказа |
|---|---|---|---|
| 1 | Достаточность | Число независимых событий после прореживания | < 300 на Discovery → «отложено» |
| 2 | Против контроля | Разница исходов с контрольной выборкой (то же время, та же волатильность) | Нет значимой разницы |
| 3 | Против эталона | Разница с эталонной реверсией К36 на сопоставимых событиях | Не лучше эталона |
| 4 | Издержки | Ожидание после издержек по базовому профилю и при ×1.5 | ≤ 0 |
| 5 | Walk-forward | Скользящие окна внутри OOS с зазором (embargo) между обучением и тестом | Отрицательное ожидание в > 40% окон |
| 6 | Bootstrap | Блочный бутстреп по дням → доверительный интервал ожидания | Нижняя граница 95% ≤ 0 |
| 7 | Monte Carlo (плацебо) | Столько же случайных сделок в тех же часах и при той же волатильности, 1000+ раз | Результат гипотезы не выше 95-го процентиля плацебо |
| 8 | Monte Carlo (порядок) | Перемешивание порядка сделок → распределение просадки | 95-й процентиль просадки выше лимита |
| 9 | Чувствительность | Окрестность параметров ±20% | Знак меняется в > 25% окрестности (нет плато) |
| 10 | Стабильность | Разбивка по годам, монетам, ТФ, сторонам, режимам | Знак разный для ETH и SOL; эффект только в одном году |
| 11 | Задержка | Вход на 1 бар позже | Эффект пропал → пометка «только лимитное исполнение» |
| 12 | Множественность | Поправка BH по всем записям журнала для этого семейства + Deflated Sharpe | Не значимо после поправки |
| 13 | Holdout | Один прогон | Ожидание ≤ 0 → отказ навсегда (новая версия = новая гипотеза с полной историей попыток) |

**Вердикты:** `REJECTED` (с причиной и номером ворот), `DEFERRED` (мало данных),
`CANDIDATE` (ворота 1–12 пройдены), `VALIDATED` (пройден holdout). Только `VALIDATED`
может стать индикатором или ботом.

## Модуль 6. Feature Importance

Цель — не прогноз цены, а ответ на вопрос «какие признаки меняют исход **события**».
Поэтому обучаем только на событиях (например, все свипы), целевая переменная — исход
по тройному барьеру после издержек. Обучение на каждом баре не используется: там почти
чистый шум, и модель выучит сезонность волатильности.

| Метод | Достоинства | Недостатки | Когда применять | Когда не применять |
|---|---|---|---|---|
| Mutual Information | Ловит нелинейные зависимости, быстро, без модели | Только по одному признаку, не видит взаимодействий; оценка шумная на малых выборках | Первичный отсев сотен признаков | Когда эффект только в комбинации |
| Random Forest (важность по Gini/MDI) | Просто, мало настроек | MDI завышает важность непрерывных и высококардинальных признаков; считается на обучающих данных | Почти никогда — только как быстрая черновая оценка | Для выводов и отчётов |
| Permutation Importance (MDA) | Считается на отложенных данных, честно отражает вклад в качество | Коррелированные признаки «прячут» друг друга; дорого | Основной метод — на purged CV | Без кластеризации коррелированных признаков |
| Clustered MDA (López de Prado) | Перемешивает целые кластеры похожих признаков → решает проблему корреляции | Нужна кластеризация признаков | **Основной вывод о важности** | Если признаков мало и они независимы |
| XGBoost / LightGBM | Сильные модели на табличных данных, взаимодействия, быстро | Легко переобучаются на финансовом шуме; много гиперпараметров | Модель-носитель для MDA и SHAP; неглубокие деревья, сильная регуляризация | Как самоцель «предсказать цену». Нужен один из двух — LightGBM быстрее |
| SHAP | Показывает направление и форму влияния, взаимодействия пар признаков | Объясняет **модель**, а не рынок; на коррелированных признаках вводит в заблуждение | Понять форму зависимости («ΔOI < −0.5% → исход лучше») и найти пары-взаимодействия для Discovery | Как доказательство edge |

**Правила:**
- Важность считается **только на Discovery**, кросс-валидация с очисткой пересекающихся
  исходов и зазором (purged CV with embargo).
- **Контрольный признак-шум** (случайная колонка) участвует всегда. Признак не важнее шума —
  неважен.
- Результат модуля — не торговое правило, а **короткий список признаков и пар** для Discovery.

## Модуль 7. Режимы рынка

Режим — это просто **признак-категория**, известный в момент t. Он строится по правилам
из уже посчитанных признаков. Скрытые марковские модели на старте не используем: у сглаженных
оценок HMM есть заглядывание в будущее, а у фильтрованных — сильное запаздывание.

| Ось | Состояния | Как определяется (пример) |
|---|---|---|
| Волатильность | low / mid / high | Процентиль ATR за 30 дней: < 30 / 30–70 / > 70 |
| Фаза волатильности | compression / expansion / neutral | Наклон ATR и ширины Bollinger |
| Тренд | trend_up / trend_down / range | Efficiency ratio и наклон на 4h |
| Плечо | oi_expansion / oi_contraction / flat | ΔOI за 24 часа по процентилям |
| Funding | crowded_long / crowded_short / neutral | Процентиль funding за 90 дней |
| Рынок | risk_on / risk_off | Тренд BTC на 1D + (в часы US) знак Nasdaq |
| Доминация | btc_led / alt_led | Ход BTC против корзины альтов за 24 часа |

**Правила:**
- Каждая гипотеза автоматически получает разбивку результатов по каждой оси отдельно.
  Полное произведение 3×3×3×3×3×2×2 = 972 ячейки не используется: в каждой ячейке почти нет данных.
- Режим, найденный полезным, становится условием `when:` обычной гипотезы. Тогда он
  проходит те же ворота и тот же учёт попыток.
- Пороги режимов фиксируются заранее по данным Discovery и дальше не подбираются.

## Модуль 8. Automatic Discovery

Полный перебор запрещён и не нужен. Задача формулируется как **поиск подгрупп** (subgroup
discovery): найти условия, при которых исход события заметно лучше, чем у всех событий
того же типа. Это известный класс задач с эффективными алгоритмами.

### Конвейер

1. **Выбор события-якоря** (свип, импульс, пробой). Поиск идёт внутри одного типа событий —
   это сужает пространство в тысячи раз и даёт осмысленную гипотезу.
2. **Дискретизация.** Каждый числовой признак режется на 5 квантилей по данным Discovery
   (границы фиксируются). Каждый интервал и каждая категория — «элемент». 300 признаков →
   примерно 1500 элементов.
3. **Одиночный отсев.** Каждый элемент против всех событий: эффект и поправка BH. Оставляем
   топ-150 плюс пары из SHAP (модуль 6).
4. **Beam search по конъюнкциям глубины ≤ 3.** Ширина луча — 50. На каждом шаге к лучшим
   50 правилам добавляется по одному элементу. Минимум 300 событий в подгруппе. Функция
   качества — нижняя граница доверительного интервала улучшения ожидания, умноженная на
   √(размер подгруппы). Это штрафует и маленькие, и слабые группы. Объём: около
   150 × 50 × 3 ≈ 22 тыс. оценок. На битовых масках событий это секунды.
5. **Второй генератор (независимый):** неглубокие деревья решений или RuleFit на тех же
   событиях. Правила, найденные обоими генераторами, получают приоритет.
6. **Удаление дублей.** Правила, покрывающие почти те же события (Jaccard > 0.7), сливаются.
7. **Выход** — YAML-гипотезы с пометкой `origin: discovery` и числом проверенных
   кандидатов. Дальше они идут обычным путём через Validation на **другом** участке истории.

### Почему не другие методы

| Метод | Вердикт |
|---|---|
| Полный перебор | Миллионы комбинаций → гарантированные ложные открытия; запрещён |
| Greedy search | Частный случай beam search с шириной 1; застревает на первом хорошем признаке |
| Beam search / subgroup discovery | **Основной.** Контролируемое число оценок, понятные правила, глубина ограничена |
| Association rules (Apriori, FP-growth) | Близкий родственник; хорош для бинарных элементов, но ищет частоту, а не улучшение исхода. Допустим как генератор кандидатов |
| Генетические и эволюционные алгоритмы | Огромное число неучтённых оценок, склонность к сложным переобученным правилам. Только после того, как платформа зрелая и журнал считает каждую оценку |
| Bayesian optimization | Не для поиска условий, а для **точной настройки параметров** уже прошедшей гипотезы. И даже там предпочтителен поиск плато, а не пика |
| Деревья / RuleFit | Второй генератор, сверка с beam search |

**Учёт попыток:** каждая оценка в Discovery — запись в журнале. При валидации правило
наследует «стоимость поиска»: порог значимости учитывает, сколько кандидатов было рассмотрено.

## Модуль 9. Метрики

Главная валюта — **ожидание в R после издержек**. Всё остальное вторично.

| Группа | Метрики |
|---|---|
| Доходность | Ожидание в R и в % после издержек; средняя сделка; profit factor; win rate (справочно); средний выигрыш и проигрыш |
| Достоверность | Число событий и эффективное число (после поправки на перекрытие и корреляцию ETH/SOL); t-статистика; доверительный интервал по бутстрепу; PSR и DSR (Deflated Sharpe); p-value после BH |
| Преимущество над нулём | **Lift к контролю** (разница с контрольной выборкой); **lift к эталону** К36; процентиль среди плацебо Monte Carlo |
| Риск | Max drawdown; 95-й процентиль просадки по Monte Carlo; время под водой; Ulcer index; хвостовой коэффициент; асимметрия |
| Риск-доходность | Sharpe, Sortino, Calmar — годовые, по дневному ряду |
| Качество сделки | MAE и MFE в R; отношение MFE/MAE; доля сделок, где цена сначала прошла +0.5R |
| Издержки | **Безубыточная комиссия** (при какой комиссии ожидание = 0); доля издержек в валовом результате; чувствительность к задержке входа |
| Время | Время удержания (медиана, хвост); сделок в месяц; доля времени в позиции |
| Устойчивость | Доля положительных лет, монет, режимов, окон walk-forward; доля положительной окрестности параметров; **тренд эффекта во времени** (затухание) |
| Сложность | Число условий; число параметров; число кандидатов, рассмотренных при поиске |
| Портфель | Корреляция с уже принятыми гипотезами — новая гипотеза ценна, если не дублирует старые |

## Модуль 10. Ранжирование

Ранжируются только гипотезы, прошедшие ворота валидации. Сортировка по win rate бессмысленна:
90% винрейта с ожиданием −0.05R — убыточная система.

### Формула

```
Score = LCB₉₅(E) × √(N_год) × Stability × Plateau × CostMargin × Novelty × (1 − 0.1 × K)
```

| Множитель | Что это | Почему так |
|---|---|---|
| LCB₉₅(E) | Нижняя граница 95%-го бутстреп-интервала ожидания в R после издержек, на OOS | Награждает не среднее, а **гарантированный минимум**. Учитывает и размер эффекта, и шум. Шумная гипотеза с высоким средним проигрывает стабильной со средним поменьше |
| √(N_год) | Корень из числа независимых сделок в год | Годовая уверенность растёт как корень из числа сделок. Корень не даёт частым, но крошечным эффектам задавить всё |
| Stability (0–1) | Доля положительных ячеек: годы × монеты × ТФ × окна walk-forward | Эффект, который живёт везде, вероятнее реален |
| Plateau (0–1) | Доля окрестности параметров ±20% с положительным ожиданием | Пик на одном значении параметра = подгонка |
| CostMargin (0–1) | min(1, безубыточная комиссия / реальная комиссия − 1) | Гипотеза, которая умирает при чуть худшем исполнении, ненадёжна |
| Novelty (0–1) | 1 − максимальная корреляция с уже принятыми гипотезами | Дубль существующей идеи ничего не добавляет |
| (1 − 0.1·K) | K — число условий в правиле | Каждое условие — степень свободы. Правило из 5 условий теряет половину очков |

**Почему произведение, а не сумма.** В сумме сильная сторона маскирует нулевую. В произведении
любой множитель около нуля обнуляет всю оценку. Гипотеза с прекрасным ожиданием, но без плато,
не попадает наверх.

Риск переобучения отдельным слагаемым не вычитается: он уже отсеян воротами (DSR,
поправка BH, плацебо, holdout) и сидит в LCB и Plateau.

## Модуль 11. Защита от переобучения

| Проблема | Как проявляется здесь | Защита в платформе |
|---|---|---|
| Переобучение | Правило с 5 условиями идеально на истории | Ограничение глубины (≤ 3), штраф за K, требование плато, отложенный период |
| Data snooping | Сотни вариаций, показываем лучшую | Журнал всех прогонов; поправка BH по семейству; Deflated Sharpe с реальным числом попыток |
| Look-ahead | Фракталы, FVG, «глубина свипа», OI с задержкой публикации, вход на баре сигнала | `available_at` в данных; заявленный `lag` у признаков; **автоматический тест причинности**; вход только со следующего бара; путь цены внутри бара по 1m, стоп раньше тейка |
| Survivorship | Для двух монет почти нет. Но: SOL выбран, потому что «выжил и вырос» | Выводы по SOL — с пометкой. При расширении списка монет брать вселенную на дату, включая делистинги |
| Selection bias | Подбор периода, монеты, ТФ, «хороших» примеров | Разбивка истории одна на проект, в конфиге; гипотеза обязана работать на обеих монетах; нельзя выбрать подпериод после просмотра результатов |
| Multiple testing | 1500 элементов × комбинации | BH на каждом уровне, стоимость поиска наследуется при валидации; отдельные участки истории для поиска и для проверки |
| Зависимость от режима | Эффект в одном режиме, ноль в среднем, или наоборот | Обязательная разбивка по осям режимов; режим как условие — только через те же ворота |
| Утечка через перекрытие | Исходы соседних событий пересекаются → завышенная t-статистика | Прореживание событий, блочный бутстреп по дням, purged CV с зазором |
| Ошибка в коде | Баг даёт фантастический результат | Санити-тест: случайные входы должны давать ожидание ≈ −издержки. Если нет — ошибка в движке |
| Подгонка исследователем | «Ещё один фильтр, и заработает» | Каждый фильтр — новая версия гипотезы в журнале; holdout одноразовый |

## Модуль 12. Структура репозитория

```
trading-indicator/
├── research/            этап 1: гипотезы и рассуждения (не трогаем, только дополняем)
├── docs/                архитектура, решения и их причины (ADR), описание наборов данных
├── src/qlab/            один Python-пакет, внутри — модули по ответственности:
│   ├── data/            загрузчики источников, очистка, манифесты, as-of соединение
│   ├── features/        по одному файлу на семейство признаков; регистрация автоматически
│   ├── events/          признаки-события (свип, импульс, пробой) и прореживание
│   ├── labels/          тройной барьер, MFE/MAE, доходности по 1m-пути
│   ├── regimes/         оси режимов
│   ├── hypotheses/      парсер YAML, язык условий, отбор событий
│   ├── backtest/        симуляция сделок, модели исполнения и комиссий
│   ├── validation/      ворота, разбивка истории, бутстреп, Monte Carlo, walk-forward
│   ├── importance/      MI, clustered MDA, SHAP
│   ├── discovery/       дискретизация, beam search, генератор на деревьях
│   ├── evaluation/      метрики и формула ранжирования
│   ├── ledger/          журнал экспериментов (только добавление)
│   └── cli.py           команды: fetch, build-features, test, discover, report
├── hypotheses/          YAML-гипотезы: manual/ и discovery/
├── configs/             разбивка истории, профили комиссий, задержки публикации, пороги ворот
├── reports/             сгенерированные отчёты (markdown + графики), в git только итоговые
├── tests/               тест причинности признаков, санити-тест движка, тесты на синтетике
└── data/                в .gitignore: raw/, clean/, cache/, ledger/
```

**Почему так:**
- **Один пакет вместо россыпи папок верхнего уровня.** Всё, что импортируется, лежит в
  `src/qlab`. Всё, что пишет человек или генерирует discovery, лежит снаружи: гипотезы, конфиги,
  отчёты.
- **Папки `strategies/` пока нет.** Стратегия появится только из гипотезы со статусом
  `VALIDATED`. Создавать её заранее — приглашение начать с неё.
- **`experiments/` = `ledger/` в `data/`.** Это журнал. В git попадают только итоговые
  отчёты, а не гигабайты прогонов.

   архива Binance за всю доступную историю.
2. **Признаки (около 6).** ATR и его процентиль, час недели, swing-уровни и свип с возвратом,
   ΔOI на свипе (с честной задержкой публикации), ход BTC в то же окно. Каждый — по контракту
   модуля 2, с тестом причинности.
3. **Разметка.** Тройной барьер по 1m-пути, исполнение со следующего бара, базовые издержки.
4. **Отчёт.** Ответы на два вопроса:
   - **Т0:** сколько ATR съедают издержки на 5m и 15m по часам недели?
   - **NIF:** различаются ли исходы свипов с ΔOI < 0 и с ΔOI > 0 при равной волатильности
     и времени, и обыгрывают ли они контрольную выборку и эталонную реверсию?

Без YAML-движка, discovery, ML и режимов: две гипотезы К1 и К2 пока проще задать прямо
в конфиге среза. Объём — 1–2 недели.

### Почему именно это первым
- **Это проверка центральной гипотезы.** От ответа зависит, куда пойдёт вся платформа.
  Если знак ΔOI не разделяет исходы, половина признаков (OI, funding, ликвидации) теряет
  приоритет, и покупать платные данные о ликвидациях не нужно.
- **Срез проходит через все слои сразу:** данные → признаки → разметка → статистика.
  Архитектура проверяется на реальном вопросе, а не на пустых абстракциях. Ошибки в контрактах
  всплывут сейчас, пока их дёшево исправить.

### Какие риски снимает
1. **Риск данных.** Есть ли история OI в архиве Binance и с какого года. Если её нет или
   она короткая, меняются разбивка истории и весь план, и лучше узнать это в первый день, а не на этапе 2.5.
2. **Риск издержек.** Если на 5m издержки съедают 0.3+ ATR, весь 5m-ТФ уходит в «только
   лимитное исполнение», и приоритеты меняются.
3. **Риск заглядывания в будущее.** Тест причинности и задержка OI проверяются на самом
   опасном месте — свипах и swing-точках.
4. **Риск «красивой платформы без результата».** Через 2 недели будет ответ про рынок,
   а не только код.

### Что разблокирует
2.2 (контракт признаков уже проверен на деле), 2.3 (разметка и контроль готовы), 2.4
(К1/К2/К36 сразу переводятся в YAML), 2.5 (есть первая реальная гипотеза для ворот),
а также решение о покупке платных данных.

### Почему остальное преждевременно
- **Discovery и ML** без проверенной разметки, издержек и защиты от look-ahead — это машина
  по производству ложных открытий. Сначала нужен надёжный измерительный прибор, потом поиск.
- **Полный backtest** со стопами, лимитками и частичными выходами не нужен, пока event study
  не показал разницы с контролем. Нечего исполнять.
- **Режимы, ранжирование, отчёты** — это способы смотреть на результаты, а результатов пока нет.
- **Платные данные** — до проверки бесплатного прокси деньги тратятся вслепую.
- **Индикатор и бот** — только из `VALIDATED`-гипотезы, которой пока не существует.
